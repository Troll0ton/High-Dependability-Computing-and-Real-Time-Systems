# RTEMS – операционная система реального времени
## Native RTEMS API vs POSIX API: планирование и IPC
RTEMS поддерживает два основных прикладных интерфейса (API) для работы с потоками и межзадачными коммуникациями: классический (Native RTEMS Classic API) и POSIX API. Classic API изначально основан на спецификации RTEID для жёсткого реального времени и предоставляет собственные вызовы RTEMS, ориентированные на особенности системы. POSIX API, напротив, соответствует стандарту POSIX (IEEE 1003.1) и обеспечивает переносимость кода с UNIX-подобных систем. Таким образом, Classic API предлагает более богатые возможности, специфичные для RTEMS, тогда как POSIX API обеспечивает совместимость и упрощает портирование кода. Например, классический API RTEMS включает средства для работы с таймерами и поддерживает планирование по методу Rate Monotonic (периодические задачи), а также тонко настраиваемые режимы выполнения потоков. В свою очередь POSIX API предоставляет condition variables (условные переменные), ключи для потоков (thread-specific data) и очереди сообщений с приоритетной сортировкой, которых нет в Classic API. Оба API поддерживают основные механизмы синхронизации (семафоры, сообщения и т.п.), но отличаются терминологией и деталями реализации. Например, Classic API оперирует объектами типа rtems_task, rtems_semaphore и т.д., в то время как POSIX использует стандартные pthread_t (потоки), pthread_mutex (мьютексы), sem_t (семафоры) и др. Внутренне реализация сервисов ОС для обоих API в RTEMS во многом общая – основной функционал ядра (планировщик, синхронизация и др.) вынесен в под系统 SuperCore, используемый обоими интерфейсами.

Планирование потоков. В RTEMS применяется приоритетное вытесняющее планирование: каждому таску/потоку присваивается приоритет, и планировщик всегда выполняет готовую задачу с наивысшим приоритетом. По умолчанию для однопроцессорной конфигурации используется алгоритм deterministic priority (фиксированные приоритеты), с опцией тайм-слиссинга (round-robin) при равных приоритетах. В многопроцессорных системах (SMP) по умолчанию включается глобальный планировщик Earliest Deadline First (EDF). Оба API (Classic и POSIX) позволяют создавать задачи с заданными приоритетами и управлять планированием, но имеют разные шкалы приоритетов. Существенное отличие: числовые значения приоритетов обратны – в Classic API низкое числовое значение означает более высокий приоритет (например, 1 – наивысший), тогда как в POSIX threads наоборот: 1 обычно трактуется как самый низкий приоритет. Таким образом, максимальный приоритет задачи в Classic API должен соответствовать наибольшему приоритетному числу в POSIX. Кроме того, различается поведение при завершении задачи: если POSIX-поток (pthread) завершает свою функцию, он просто тихо уничтожается системой, тогда как в Classic API выход из задачи через rtems_task_exit рассматривается как фатальная ошибка (задачи обычно не должны самопроизвольно завершаться). В целом, оба API могут использоваться одновременно в одном приложении на RTEMS (т.е. задачи и ресурсы Classic и POSIX могут сосуществовать) – их реализации взаимодействуют через общие механизмы ядра. Например, POSIX-вызовы sockets или termios внутри используют внутренние семафоры и события Classic API.

Механизмы IPC (взаимодействие задач). RTEMS предоставляет богатый набор средств межзадачной коммуникации и синхронизации в рамках обоих API. Classic API включает объекты семафоров (rtems_semaphore_* — бинарных или счетных, с поддержкой протоколов приоритетного наследования/ceilings), очередей сообщений (rtems_message_queue_*), событий (набор битовых флагов, которые одна задача может устанавливать для другой) и сигналов (асинхронные уведомления задачам) и др. Также Classic API имеет менеджер таймеров и Rate Monotonic менеджер для реализации периодических задач с контролем дедлайнов. POSIX API предоставляет аналогичные возможности, используя стандартные средства: POSIX-семафоры (sem_init/sem_wait/...), мьютексы (pthread_mutex_*), условные переменные (pthread_cond_*), POSIX-сигналы (pthread_kill/sigaction для потоков) и очереди сообщений (mq_open/mq_send/...). POSIX message queue поддерживает приоритет сообщений, что отсутствует в классических очередях RTEMS. Некоторые уникальные возможности Classic API (например, механизм периодических задач Rate Monotonic) не имеют прямого эквивалента в POSIX и реализуются через сочетание POSIX-таймеров и семафоров или за счет использования соответствующих менеджеров Classic API. С другой стороны, POSIX API даёт совместимость со стандартной библиотекой Си (функции ввода-вывода, потоковые I/O), которые в RTEMS всегда доступны; а runtime-библиотеки (например, GNU Ada) реализованы поверх POSIX-совместимых потоков.

Ada Tasking в RTEMS. Язык Ada обладает встроенной моделью тасков (многопоточности), и поддержка Ada в RTEMS достигается благодаря POSIX-совместимости ядра. Каждый поток Ada (задача Ada) при работе через компилятор GNAT отображается на POSIX-поток ОС RTEMS. Соответственно, приоритеты Ada-тасков транслируются в диапазон приоритетов POSIX-потоков. Это означает, что нужно учитывать различия шкал: Ada имеет собственный дискретный диапазон приоритетов, который GNAT/RTEMS отображает на приоритеты pthread; при этом низшие числовые значения приоритета Ada соответствуют высшему приоритету Classic RTEMS, тогда как для POSIX-потоков – наоборот. Разработчикам следует быть внимательными при смешивании в одном приложении задач Ada, Classic и POSIX: в документации RTEMS отмечено, что полезно составить таблицу соответствия всех используемых приоритетов в разных моделях задач. В целом же, нативные Ada-таски могут работать на RTEMS без модификаций, а рантайм GNAT сам использует сервисы POSIX (например, мьютекс с потолком приоритетов) для синхронизации внутренних структур. Также в RTEMS имеется специальный биндинг Ada для части Classic API, позволяющий вызывать функции RTEMS (например, rtems_task_create) из кода на Ada, однако он охватывает не все возможности и расширяется по запросу пользователей.

## Архитектура RTEMS: BSP, ядро, драйверы, файловая система
ОС RTEMS заметно отличается по архитектуре от универсальных Unix-подобных ОС. RTEMS не поддерживает многопользовательскую интерактивную работу, запуск программ из shell в runtime или динамическую загрузку исполняемых модулей так, как это делает, скажем, Linux. Вместо этого RTEMS представляет собой монолитное ядро (executive), которое компонуется статически с пользовательским приложением и предоставляет ему сервисы ОС реального времени. Фактически приложение и ОС образуют единый образ программы, исполняющийся на «голом железе». Ниже рассмотрены основные архитектурные слои RTEMS:
• Board Support Package (BSP) – пакет поддержки платы. BSP – это аппаратно-зависимый слой RTEMS, содержащий код и драйверы для конкретной целевой платы или процессорной архитектуры. С него начинается выполнение системы при старте. В BSP входят процедуры начальной инициализации процессора и устройств (например, настройка контроллера тактов, отключение прерываний, инициализация SRAM/DDR, таблицы векторов прерываний и т.д.). Кроме того, BSP обычно включает драйверы основных периферийных устройств конкретной платы: консольного UART порта, таймера системных тиков, контроллеров прерываний, сетевых интерфейсов, дисковых контроллеров и проч. – то есть всего, что необходимо для базового ввода-вывода на данной аппаратуре. BSP обеспечивает интерфейс между ядром RTEMS и «железом», изолируя остальной код ОС от подробностей конкретной архитектуры. Благодаря четкому разделению, RTEMS сравнительно легко портировать на новые платформы – как отмечали разработчики, все архитектурно-зависимые части отделены от остального кода. В настоящий момент RTEMS поддерживает большое число архитектур CPU – по данным проекта, RTEMS работает на 18 различных семействах процессоров, включая ARM, PowerPC, Intel x86, SPARC (LEON), RISC-V, MIPS и другие. Под каждую архитектуру в составе RTEMS существует набор BSP для конкретных плат/микроконтроллеров (всего порядка 200 BSP для различных устройств).
• Ядро RTEMS – располагается выше BSP и реализует собственно функции ОС реального времени. Это сердце системы, отвечающее за планирование задач, управление прерываниями, синхронизацию, таймеры, управление памятью и пр. Ядро написано в основном на С и ассемблере и не зависит от прикладной области – оно предоставляет набор так называемых менеджеров (managers) для различных услуг: менеджер задач (создание/управление задачами), менеджер семафоров, сообщений, событий, менеджер времени (таймеры, задержки, часы), менеджер памяти и др. Данные сервисы доступны приложению через API (Classic или POSIX), но внутренняя реализация сосредоточена в едином ядре. RTEMS реализует единую адресную пространство – задачи выполняются в привилегированном режиме, разделения на «ядро» и «пользовательские процессы» нет, что упрощает и ускоряет взаимодействие, хотя и требует осторожности (например, ошибки приложения могут нарушить работу всего системы). Архитектура ядра модульная: как упоминалось, большая часть функционала ОС (SuperCore) используется обоими API. Выше ядра могут подключаться дополнительные подсистемы: например, стек протоколов TCP/IP (в RTEMS интегрирован стек из FreeBSD) и драйверы сетевых устройств, файловые системы, реализация POSIX-суместимых вызовов libc и т.п. В отличие от настольных ОС, в RTEMS по умолчанию отсутствует интерактивный shell и возможность загрузки новых процессов во время работы – все задачи определяются заранее в программе. (Современные версии RTEMS, впрочем, предоставляют опциональный встроенный консольный shell и поддержку динамической загрузки модулей, что может использоваться для отладки или расширения приложения. Эти возможности не нарушают принципов RTEMS, но применяются по необходимости и обычно отключены в жёстко реальном времени для экономии ресурсов и предсказуемости выполнения.)
• Драйверы внешних устройств. RTEMS включает систему ввода-вывода и драйверов, позволяющую работать с оборудованием через унифицированные вызовы (open/close/read/write и пр.). Драйверы встраиваются в образ приложения и выполняются в том же контексте, что и задачи (либо в контексте обработчиков прерываний, если это ISR). Низкоуровневые драйверы часто являются частью BSP – например, драйвер тактового таймера (генерирует системный тик с заданной периодичностью) обычно реализован в BSP, драйвер последовательного порта консоли – там же. RTEMS предоставляет менеджер ввода-вывода (I/O manager), через который драйверы регистрируются и вызываются стандартными системными вызовами. В системе нет разделения на “ядро/пользователь” режим, поэтому драйверы могут напрямую вызывать функции ядра и управлять аппаратурой. RTEMS поддерживает также драйверы сетевых интерфейсов (через стек TCP/IP), драйверы дисковых устройств (для файловых систем) и др. Уровень драйверов можно условно считать частью ОС, расположенной между ядром и прикладными задачами: задачи вызывают, например, open("/dev/console", ...), которая перенаправляется ядром на соответствующую функцию драйвера консоли в BSP. Таким образом, драйверы “подключаются” к ядру через таблицы в BSP. В целом, архитектура RTEMS строится слоями: аппаратура -> BSP/драйверы -> ядро (SuperCore + менеджеры) -> прикладное ПО.
• Файловая система. Несмотря на специфичность для встроенных систем, RTEMS поддерживает работу с файловыми системами. В RTEMS реализовано несколько файловых систем: имеется собственная легковесная файловая система IMFS (In-Memory FS) для представления устройств и файлов в памяти, а также порты более сложных FS из BSD и POSIX. В частности, RTEMS включает поддержку NFS (Network File System) и FAT (FAT16/32) среди прочих. Кроме того, разработаны специально адаптированные для реального времени файловые системы – например, RTEMS FS (RFS) и TFTP-FS, которые учитывают особенности встроенного хранения данных. Наличие файловой системы в ОСРВ может вызвать вопрос о влиянии на детерминизм: действительно, операции файлового ввода-вывода (особенно на медленные носители или по сети) могут иметь непредсказуемые задержки. В RTEMS этот риск митигируется тем, что файловые системы обычно используются либо в простых случаях (например, FAT на локальной Flash-памяти для хранения логов) либо в виде RAM-диска. Разработчик системы сам контролирует, когда и где выполнять файловые операции. Доступ к файлам в реальном времени возможен, но рекомендуется выносить его в отдельные задачи низкого приоритета, чтобы возможные задержки не влияли на критичные потоки. Таким образом, наличие файловой системы не противоречит обеспечению гарантий реального времени*, если использовать её разумно. RTEMS, будучи ОС общего назначения для встроенных систем, предоставляет инструменты, а вопрос детерминизма решается архитектурой приложения. Отметим, что сети и файловые службы в RTEMS заимствованы из UNIX (стек TCP/IP из FreeBSD и др.) и не всегда рассчитаны на жёсткие временные ограничения – например, штатный стек TCP/IP обеспечивает полноту протоколов, но в худшем случае для гарантированного времени обработки пакетов может потребоваться избыточное резервирование ресурсов. В критичных системах допускается использовать упрощённые или специально спроектированные файловые подсистемы, либо отключать их совсем. В целом же RTEMS предоставляет разработчику выбор: можно собрать минимальную конфигурацию ядра без файловой системы, либо включить необходимую файловую и сетевую функциональность (например, для вывода телеметрии или обновления ПО), оценив влияние на временные характеристики.
## Сравнение RTEMS с FreeRTOS и μC/OS-III
Рассмотрим кратко, чем RTEMS отличается от двух других широко известных открытых ОСРВ – FreeRTOS и μC/OS-III, – и для каких областей каждая из них наиболее подходит. Все три – open-source RTOS, но имеют различную историю и оптимизацию под разные масштабы задач:
• RTEMS: полнофункциональная реалтайм ОС, ориентированная на применение в высоконадежных системах (авиакосмическая отрасль, военная техника, промышленные контроллеры). RTEMS поддерживает множество архитектур и обладает богатым набором возможностей: многозадачность с приоритетами, SMP (мультипроцессорность), стандарт POSIX, сетевой стек TCP/IP, драйверы устройств, файловые системы и др.. По сути, RTEMS ближе к классическим ОС (типа VxWorks) – она может одновременно выполнять множество задач, поддерживает сложные протоколы и сервисы. Это сказывается и на требуемых ресурсах: RTEMS обычно используется на сравнительно мощных встраиваемых платформах (32-разрядные и 64-разрядные CPU с десятками мегагерц и выше, наличие ОЗУ от сотен килобайт до мегабайт). Зато взамен предоставляется более богатая среда: например, можно сравнительно легко портировать на RTEMS существующий сетевой сервис или стек, написанный под POSIX. RTEMS широко применяется там, где нужны стандартизированные интерфейсы и сложная функциональность. Так, RTEMS выбрана в ряде космических проектов NASA и ESA – эта ОС используется на борту марсианского орбитального модуля MRO (радиосистема Electra) и европейского зонда TGO, а также на солнечном зонде Parker Probe. Популярна RTEMS и в научных установках (например, в системе управления экспериментов EPICS) и других областях, требующих надежности. В сравнении с FreeRTOS и μC/OS, RTEMS чаще подходит для случаев, когда система сложная и ресурсоемкая, требуется поддержка множества задач, файлов/сетей, а железо позволяет использовать более “тяжелую” ОС. Если же проект рассчитан на совсем малый микроконтроллер или требует минимального вмешательства ОС, RTEMS может быть избыточной. Но когда приоритет – сокращение времени разработки за счет использования готовых компонентов (сетевых стеков, файловых систем и т.п.) и переносимости кода, RTEMS даёт преимущество – конечно, при условии достаточной вычислительной мощности целевого устройства.
• FreeRTOS: максимально компактное ядро ОС реального времени, нацеленное на небольшие микроконтроллеры и встроенные системы с ограниченными ресурсами. FreeRTOS существенно проще по дизайну, чем RTEMS: по сути, это ядро планирования задач с базовыми примитивами синхронизации (семафоры, очереди сообщений, мутексы) и программными таймерами. FreeRTOS не стремится соответствовать POSIX и имеет собственный API, очень простой в освоении. Размер ядра исчисляется несколькими килобайтами Flash и сотнями байт RAM, что позволяет запускать FreeRTOS даже на 8- и 16-разрядных МК. Эта ОС невероятно популярна в индустрии IoT и встраиваемых приложений: как отмечается, FreeRTOS – один из самых широко используемых RTOS в мире, поддерживаемый на множестве МК различной архитектуры. Amazon (AWS) курирует развитие FreeRTOS, встроив в него библиотеки для подключения к облаку и повышенной безопасности, что делает FreeRTOS привлекательной для интернет-вещей. Область применения FreeRTOS – это малые системы, где требуется управление несколькими задачами в реальном времени без лишних накладных расходов. Например, носимые устройства, датчики, бытовая техника на микроконтроллерах – там FreeRTOS зачастую оптимален. У FreeRTOS огромное сообщество и множество примеров, что упрощает поддержку. С другой стороны, FreeRTOS не предоставляет «из коробки» таких возможностей, как файловая система или сложный сетевой стек – лишь основные компоненты ядра. При необходимости их добавляют отдельно (существуют дополнительные библиотеки FreeRTOS+TCP, FreeRTOS+FAT и др.). Таким образом, FreeRTOS оптимальна для простых по логике, ресурс-ограниченных устройств, где важна минимальная загрузка CPU/памяти и разработчики готовы самостоятельно интегрировать дополнительные компоненты по мере необходимости. В случаях же, когда требуется масштабируемость или стандартизованные интерфейсы, могут предпочесть более крупные ОС (типа RTEMS или Zephyr).
• μC/OS-III (Micrium OS): исторически коммерческая ОСРВ, ныне доступная под открытой лицензией (Apache 2.0). Отличается строгой детерминированностью и проверенностью в промышленности. Семейство μC/OS (включая предыдущую версию μC/OS-II) известно тем, что использовалось в критически важных системах – медицинских приборах, авиационной электронике, автомобильных контроллерах – благодаря тому, что ядро прошло сертификации по стандартам безопасности (например, DO-178B для авиации, IEC 61508 SIL3, FDA Class III и др.). μC/OS-III имеет очень аккуратную архитектуру и богато документировано – автор µC/OS Жан Лабросс выпустил подробные книги с разбором исходного кода, что свидетельствует о степени проработки системы. В сравнении с FreeRTOS, μC/OS обычно несколько более объемна (ядро порядка нескольких килобайт, поддерживает до сотен задач, управляет ими по приоритетам, поддерживает разделение времени) и предоставляет немного более широкий функционал (например, есть встроенные счетчики событий, флаги). Главное же – упор на надежность и аналитику: μC/OS имеет функции трассировки, пикового использования стека и др. Сейчас проект μC/OS-III открыт и поддерживается компанией Weston Embedded (после приобретения Micrium корпорацией Silicon Labs). Weston предоставляет и коммерческие услуги: обновления, техподдержку и пакеты для сертификации под различные стандарты. Типичные области применения μC/OS-III – там, где критически важно гарантировать своевременность и корректность работы, и при этом система не слишком сложна по размеру. Например, медицинское устройство с микроконтроллером может использовать μC/OS, чтобы легче пройти сертификацию FDA, благодаря наличию готовых отчетов и проверок. Или автомобильный контроллер ABS, где требуется доказанная надежность – μC/OS для таких задач подходит благодаря детерминизму и проверенной репутации. Сейчас, когда μC/OS стал открытым, его также могут выбирать в проектах, требующих качественного, но легковесного ядра: отмечается, что μC/OS идеально подходит для встроенных систем, чувствительных к стоимости и не крайне критичных, где нужна проверенная временем ОС с минимальными накладными расходами. В случае же очень строгих критичных проектов разработчики могут приобрести у Weston Embedded расширенный вариант (CesiumRTOS) или сертификационные материалы под μC/OS. В сравнении с RTEMS, μC/OS-III рассчитана скорее на мономашинные контроллеры и не имеет встроенных сетевых стеков или файловых систем (Micrium предлагала их отдельными модулями – μC/TCP-IP, μC/FS и т.д., тоже коммерческими). Поэтому μC/OS применяют, когда система может быть относительно изолированной и выполняет одну главную функцию, требующую надежного планирования.
Подводя итог, RTEMS, FreeRTOS и μC/OS-III отличаются масштабом и сферой оптимального применения. RTEMS – более тяжелая и функционально насыщенная ОСРВ, часто используемая в наукоемких и критичных областях (космос, оборона, большие промышленные системы), где нужны стандарты (POSIX), сложные коммуникации и мультипроцессорность. FreeRTOS – сверхлегкий и простой RTOS для массовых небольших устройств и IoT, где важнее минимализм и поддержка сообществом. μC/OS-III занимает промежуточное положение: используется в ответственных встраиваемых системах, требующих сертификации и строгой детерминированности, особенно когда проект готов следовать проверенным шаблонам и, при необходимости, получать коммерческую поддержку. Каждый из этих RTOS обладает своими сильными сторонами, и выбор зависит от требований конкретного проекта.
